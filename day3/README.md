# Day 3, Task 3.2: call, apply, bind

## Объяснение

**Разница между call и apply.**
Они делают абсолютно одно и то же: вызывают функцию немедленно с указанным `this`. Разница только в синтаксисе передачи аргументов: `call(this, arg1, arg2)` против `apply(this, [arg1, arg2])`. `apply` удобен, когда аргументы уже лежат в массиве (например, `Math.max.apply(null, [1, 5, 3])`).

**Как работает bind.**
Метод `bind` не вызывает функцию. Он создает и возвращает **новую функцию-обёртку**. Внутри этой обёртки оригинальная функция вызывается через `call` или `apply` с тем `this`, который был передан в `bind`. Также `bind` поддерживает частичное применение (каррирование): аргументы, переданные в `bind`, фиксируются первыми.

**Почему повторный bind не меняет контекст.**
Это фундаментальное свойство `bind`. Когда мы делаем `const fn2 = fn1.bind(obj)`, создается обёртка, которая **навсегда** запоминает `obj` в своём замыкании.
Если мы попытаемся сделать `const fn3 = fn2.bind(otherObj)`, метод `bind` видит, что `fn2` — это уже специальная "привязанная" функция (в спецификации ECMAScript у таких функций есть внутренний флаг `[[BoundThis]]`). В этом случае новый `bind` просто игнорирует переданный `otherObj` и возвращает функцию, которая всё равно будет использовать исходный `obj`.

Это сделано намеренно для безопасности: если библиотека или фреймворк привязал контекст к функции, сторонний код не должен иметь возможности это сломать.

## Проверка

- ✅ `call` корректно подменяет `this` для трех разных объектов.
- ✅ `apply` корректно принимает массив аргументов.
- ✅ `bind` создает готовую функцию с зафиксированным `this`.
- ✅ Повторный `bind` не переопределяет уже установленный контекст.
- ✅ Все проверки `console.assert` пройдены.

# Task 3.4: Стрелка внутри метода

## Объяснение

**Почему стрелка берёт this внешнего метода.**

Стрелочная функция фундаментально отличается от обычной: у неё **нет своего `this`**. Когда интерпретатор встречает `this` внутри стрелки, он не смотрит, как её вызвали. Вместо этого он идёт вверх по лексическим областям видимости и берёт `this` из ближайшей внешней не-стрелочной функции.

В нашем случае:

1. Метод `startWithArrow()` вызван как `timerController.startWithArrow()`. Значит, `this` внутри метода равен `timerController`.
2. Внутри метода создаётся стрелка `() => { ... }`. Она "видит" `this` метода через замыкание.
3. Когда `setTimeout` вызывает эту стрелку через 100 мс, стрелка всё равно использует тот же `this`, что и метод — то есть `timerController`.

Это главное преимущество стрелок: они автоматически "наследуют" контекст, и не нужно писать `.bind(this)`.

**Почему стрелочный метод объекта неудобен.**

Когда мы пишем:

```javascript
const obj = {
  name: "Test",
  printName: () => {
    console.log(this.name);
  },
};
```

Стрелка printName создаётся не внутри другой функции, а прямо в объектном литерале. У объектного литерала нет своей лексической области видимости — он просто создаёт свойства. Поэтому стрелка идёт дальше вверх и находит this из модуля, а в модуле this === undefined.
Результат: obj.printName() выведет undefined, хотя мы ожидали "Test". Объект слева от точки игнорируется, потому что стрелке всё равно, как её вызвали.

## Проверка

✅ Обычный callback теряет this (равен undefined).
✅ Callback с bind сохраняет this объекта.
✅ Стрелка внутри метода берёт this из метода и корректно работает в setTimeout.
✅ Стрелочный метод объекта теряет this (объект слева от точки игнорируется).
✅ Все console.assert пройдены.

# Task 3.5: Контроллер с жизненным циклом

## Сохранённые ссылки на callbacks

Контроллер хранит следующие ссылки:

1. **`boundHandleStart`** — привязанная функция `handleStart.bind(this)`. Используется для добавления и удаления обработчика на кнопке Start.
2. **`boundHandleReset`** — привязанная функция `handleReset.bind(this)`. Используется для добавления и удаления обработчика на кнопке Reset.

Эти ссылки создаются один раз в `init()` и сохраняются в свойствах объекта. В `destroy()` мы используем именно эти сохранённые ссылки для `removeEventListener`, что гарантирует корректное удаление обработчиков.

## Объяснение

**Почему bind() не создаётся внутри removeEventListener.**

Метод `bind()` **всегда** возвращает новую функцию. Если мы напишем:

```javascript
btn.addEventListener("click", this.handleStart.bind(this));
// ...позже...
btn.removeEventListener("click", this.handleStart.bind(this)); // НЕ СРАБОТАЕТ!
```

removeEventListener не найдёт обработчик, потому что мы передаём ему новую ссылку на функцию, а не ту, что была добавлена. Поэтому мы обязаны создать привязанную функцию один раз, сохранить её в свойстве (this.boundHandleStart), и использовать эту же ссылку для добавления и удаления.

Почему this объясняется формой вызова.

Когда мы вызываем appController.handleStart(), объект слева от точки становится this внутри метода. Но если мы сохраним ссылку на метод в переменную (const fn = appController.handleStart) и вызовем её как fn(), контекст теряется — в модуле this === undefined. Именно поэтому мы используем bind(this) при инициализации: он создаёт новую функцию, у которой this жёстко зафиксирован на appController, независимо от того, как её вызовут.

Почему destroy() работает.

destroy() делает три вещи:

Удаляет обработчики через removeEventListener, используя сохранённые ссылки boundHandleStart и boundHandleReset.
Обнуляет эти ссылки (= null), освобождая память.
Сбрасывает флаг isInitialized = false, чтобы можно было снова вызвать init() в будущем.
После destroy() кнопки не реагируют на клики, потому что обработчики физически удалены из DOM-элементов.

# Проверка дня

✅ bind() не создаётся внутри removeEventListener: привязанные функции создаются один раз в init() и сохраняются в свойствах.
✅ this объясняется формой вызова: метод handleStart() получает this при вызове через точку (appController.handleStart()), но теряет его при отдельном вызове.
✅ У контроллера работает destroy(): обработчики удаляются, состояние сбрасывается, кнопки перестают реагировать.
