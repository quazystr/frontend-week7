## Task 6.4: Настройки и debounce

### Решение по Reset: cancel(), а не flush()

При Reset мы вызываем `debouncedSave.cancel()`, а не `flush()`.

**Почему cancel:**
Reset — это откат к последнему сохранённому состоянию. Если пользователь ввёл новое значение, но не дождался сохранения, и нажал Reset, он явно говорит: "я передумал, верни как было". Вызов `flush()` в этой ситуации сохранил бы новое (возможно, нежелательное) значение, что противоречит смыслу Reset.

**Когда был бы уместен flush:**
Если бы Reset означал "применить все изменения и начать заново" (как в формах с кнопкой "Сохранить и сбросить"). Но в нашем случае Reset — это именно отмена изменений.

**Как это работает:**

1. Пользователь вводит `50` в поле "Фокус".
2. `setFocusMinutes(50)` обновляет `current.focusMinutes` в памяти и планирует `debouncedSave` через 400 мс.
3. Пользователь нажимает Reset до истечения 400 мс.
4. `reset()` вызывает `debouncedSave.cancel()` — таймер отменяется, значение `50` НЕ попадает в localStorage.
5. `reset()` перечитывает значения из localStorage — это и есть "последнее сохранённое состояние".
6. Поля ввода обновляются до сохранённых значений.

### Результат

Все 7 групп тестов прошли:

1. Валидация границ (1, 90, 0, 91, -1, 1.5, NaN, "abc").
2. Debounce: быстрые изменения дают одно сохранение последнего значения.
3. Reset отменяет debounce — невалидное значение не попадает в storage.
4. Чтение сохранённых настроек при создании.
5. getFocusMs/getBreakMs возвращают миллисекунды.
6. Некорректное значение не меняет состояние, есть сообщение об ошибке.
7. Повреждённый JSON не ломает создание.

### Проверка

- ✅ Длительность 1-90 минут, валидация на границах.
- ✅ Сохранение через debounce(400 мс).
- ✅ Некорректное значение показывает ошибку, не ломает сессию.
- ✅ Reset отменяет ожидающее сохранение через cancel().
- ✅ Все console.assert пройдены.
