# Day 2, Task 2-5: Освобождение ресурсов

## 1. Прогноз

Ожидаю, что:

- `createAutoSaver(save, delay)` создаёт замыкание с приватными переменными `timerId` и `pendingValue`.
- `schedule(value)` отменяет предыдущий таймер (если был) и планирует новый. Это обеспечивает "ленивое" сохранение: если пользователь быстро печатает, сохраняется только последнее значение.
- `flush()` немедленно вызывает `save(pendingValue)`, если есть отложенное значение, и отменяет таймер.
- `cancel()` отменяет таймер через `clearTimeout` и сбрасывает `pendingValue`. После `cancel()` старый callback **не выполнится**, потому что мы физически отменили его в планировщике браузера.
- Два экземпляра автосейвера работают независимо: у каждого своё замыкание со своими `timerId` и `pendingValue`.
- Приватные переменные недоступны снаружи: `saver.timerId === undefined`.

## 3. Объяснение

**Почему cancel() останавливает callback.**

Когда мы вызываем `setTimeout(fn, delay)`, браузер возвращает числовой ID и регистрирует задачу в своём внутреннем планировщике. Функция `clearTimeout(id)` говорит браузеру: "удали эту задачу из планировщика, она больше не нужна". После `clearTimeout` браузер физически не вызовет `fn`, даже если время ещё не вышло. Поэтому наш callback, который должен был вызвать `save(pendingValue)`, просто не выполнится.

Важно: мы также обнуляем `timerId` и `pendingValue` в `cancel()`. Это значит, что даже если бы каким-то чудом callback выполнился (что невозможно после `clearTimeout`), он бы не имел доступа к старому значению.

**Почему flush() работает.**

`flush()` делает то же, что и callback таймера, но немедленно: отменяет таймер через `clearTimeout` и сразу вызывает `save(pendingValue)`. Это полезно, например, когда пользователь закрывает страницу — нужно сохранить последнее значение, не дожидаясь задержки.

**Что удерживает замыкание.**

Каждый экземпляр автосейвера через замыкание удерживает ссылки на:

1. **`save`** — функция сохранения, переданная в фабрику. Пока существует автосейвер, эта функция не будет удалена сборщиком мусора.
2. **`delay`** — число, примитив. Занимает ничтожно мало памяти.
3. **`timerId`** — число (ID таймера) или `null`. Тоже примитив.
4. **`pendingValue`** — значение, переданное в последний `schedule()`. **Вот здесь кроется опасность.**

**Почему ссылка на большой DOM-узел внутри замыкания — плохая идея.**

Представим такой код:

```javascript
const hugeDiv = document.querySelector(".massive-table"); // тысячи узлов
const saver = createAutoSaver((value) => {
  // ...сохраняем hugeDiv.outerHTML...
}, 1000);

saver.schedule(hugeDiv);
```

После schedule(hugeDiv) переменная pendingValue внутри замыкания автосейвера хранит ссылку на hugeDiv. Это значит:

Сборщик мусора не может удалить hugeDiv, даже если мы удалим его из DOM через hugeDiv.remove(). Потому что на него всё ещё ссылается pendingValue в замыкании.

Утечка памяти: hugeDiv со всеми дочерними элементами, обработчиками событий и данными остаётся в памяти до тех пор, пока:

- не сработает таймер (тогда pendingValue обнулится внутри callback),
- или мы не вызовем cancel() (он обнулит pendingValue),
- или сам автосейвер не станет недостижимым.

Если автосейвер живёт долго (например, создан один раз при загрузке страницы и живёт всё время), а DOM-узел должен был быть удалён (например, при переходе на другую вкладку SPA), мы получаем классическую утечку памяти.

Правило: в замыкании, которое живёт долго, не должны храниться ссылки на большие объекты, DOM-узлы или данные, которые должны быть удалены. Если нужно сохранить что-то тяжёлое — лучше хранить только ID или лёгкий дескриптор, а сам объект искать заново в момент использования.
Как мы защитились в этом задании.

В нашем cancel() мы обнуляем pendingValue = undefined. Это значит, что даже если пользователь передал в schedule() большой объект, после cancel() ссылка на него исчезает, и сборщик мусора сможет его удалить. Это важный паттерн освобождения ресурсов.
